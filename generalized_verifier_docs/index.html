Generalized Verifier: Evidence-Based Analysis

This document highlights specific, empirically-proven failure modes observed in the four evaluation trials (e.g., Trial-01 chats, global-direct-iter14-midband-eval-full-chat.html), isolating the root causes, model mistakes, and the required generalized verifier boundaries to resolve them.

🚨 Part 1: The Root Causes (Environmental & Contract Defects)

Before evaluating model intelligence, two critical infrastructure defects guaranteed a 0% pass rate on specific tasks. These must be caught by Environmental/Contract Verifiers.

Root Cause 1: Hidden API Contract in Prompts 0/7,680 Outcomes

The Reality: The prompt did not provide function signatures, and the injected `.h` file contained only an empty namespace. The model was forced to invent signatures. This is the ultimate root cause of missing enums, template placement errors, and private constructors (e.g., Bank Account).

🔴 Old System
Allowed the model to blindly guess the API. When the test harness called an exact signature, it resulted in massive CE (Compile Errors).
🟢 Generalized Fix
Prompt Injection + AST Gate: The exact API contract must be explicitly provided. An AST Structural Gate then verifies the contract before passing it to C++.

Root Cause 2: Unwinnable Environment (CMake Boost Defect) Environment

The Reality: Two tasks were fundamentally unwinnable because the CMake configuration contained find_package(Boost REQUIRED), which aborted the build before compilation even started due to a missing environment dependency.

🔴 Old System
Treated the CMake abort as a model failure (Compile Error), forcing the RL model to try to fix C++ code to solve a missing OS package.
🟢 Generalized Fix
Environmental Verdict (INVALID): Perform a CMake dry-run. If configuration fails, return an INVALID environment state to prevent corrupting the RL gradient.

🧠 Part 2: Behavioral Mistakes & Generalized Verification

Mistake 1: Constructor Visibility Bank Account

The Error (Verified in Trial-01): The model literally wrote // Private constructor to ensure proper initialization, resulting in the error: 'Bankaccount::Bankaccount::Bankaccount()' is private within this context.

🔴 Old Verifier
Relied entirely on the C++ compiler's generic output, obfuscating a simple structural error.
🟢 New Verifier (Structural API Gate — generalized)
01_structural_api_gate.py: derives the required API from the official test file (ns::Ident chains), then checks the candidate declares each symbol in the right namespace, as a template when the test uses X<T>, and with a public constructor when the test constructs it. Zero task names in the verifier; feedback is exact: "'…' constructor is private". 
required = required_symbols_from_test(test_code)   # e.g. ns::Type used by the test
model    = parse_candidate(header_code, cpp_code)  # namespaces + access sections
if decl.ctor_access and 'public' not in decl.ctor_access:
    fail(f"'{ident}' constructor is {decl.ctor_access[0]} -- the test "
         f"constructs '{ns}::{ident}' and needs a public constructor")

Mistake 2: State Lifecycle & Reset Logic Bank Account

The Error: The model failed to reset the account balance on close(). Turn-1 failures frequently halted on "close semantics."

🔴 Old Verifier
Used the standard concurrency test suite, which failed cryptically if state leaked between tests.
🟢 New Verifier (Metamorphic Testing)
Injects a boundary test to check specific lifecycle transitions (open -> deposit -> close -> open) before running complex harnesses.

Mistake 3: CE vs LE Coarse Attribution Linked List / General

The Error: The model mismatched declarations (header) and definitions (cpp), causing undefined reference errors. The old system flattened 12 failed kernels into a generic "Compile Error."

🔴 Old Verifier
Single-step build (g++ -o). The RL loop penalized the model for a generic CE, leading it to rewrite logic instead of fixing headers.
🟢 New Verifier (Two-Stage Build — real subprocess)
03_two_stage_build_verifier.py: Stage 1 compiles the candidate TU alone (-c), Stage 2 compiles the official test + test/tests-main.cpp against it and links. Classifies CE-1 / CE-2 / LE (detects undefined reference) / PASS. Task-agnostic by construction: everything comes from --fixture-dir and the candidate paths. 
# Stage 2 link step:
rc, err = run([CXX, stem+".o", stem+"_test.o", "tests-main.o", "-o", binary])
if rc != 0 and "undefined reference" in err:
    return LE, "LINKER ERROR: declared in the header but never defined. "
               "Move the definitions into the header."

Mistake 4: -Werror & Algorithmic Flaws Crypto Square

The Error (Empirical Evidence): The model successfully defined the API, but consistently failed due to -Werror=unused-parameter ('text'). In Turn 2 repairs, the algorithm was simply wrong (e.g., returning segmented plaintext instead of the cipher, double-space padding issues).

🔴 Old Verifier
Failed to differentiate between a strict compiler warning failure and a deep algorithmic logic failure.
🟢 New Verifier (Differential Semantic Gate — generalized)
04_differential_semantic_verifier.py: builds the fixture's .meta/example.* reference as a positive control (must pass 100%, else the task package is reported broken), then runs the candidate's test binary and reports Catch2 passed/total assertions as partial credit (a gradient), plus a differential verdict: any assertion the reference passes but the candidate fails is a semantic regression. The observed "returns the input essentially unchanged" failure is caught by this differential — a fully generic echo probe is impossible without task knowledge (documented in the module docstring), so no per-task strings are hardcoded. 
ref_run  = run_test_binary(ref_binary)    # positive control: must be 100%
cand_run = run_test_binary(cand_binary)   # partial credit = passed/total
if ref_run.score == 1.0 and cand_run.score < 1.0:
    report("semantic regression, not a build problem")

Mistake 5: Generation Budget Exhaustion (Runaway Thinking) Crypto Square

The Error: It was not context exhaustion (prompts were only 1.3-7k tokens). The model burned its 32,768 output generation budget meandering inside the THINKING block, or silently hit EOS. 77/83 times, the actual correct solution was sitting fully formed inside the thinking log.

🔴 Old Verifier
Treated it as a timeout/compile failure. Caution: Simply applying a flat `-1` penalty for truncated rows was proven to amplify loops (12% → 41%) during training.
🟢 New Verifier (Retry/Masking Strategy)
For Eval: Implements "Retry-on-Empty" by parsing the THINKING block to extract the ready solution.
For Training: Applies gradient masking rather than a flat `-1` to avoid amplifying runaway loops.

⚙️ Conceptual Precision: How the Model Learns

It is critical to distinguish between the two separate learning phases in this pipeline:

  1. In-Episode Recovery (The Rollout / Aider Retry): When the verifier generates textual feedback (e.g., "Constructor is private"), the model reads this text during Turn-2. This allows the model to attempt a repair within the same chat trajectory.
  2. GRPO Weight Updates (The Math): When the trajectory ends, the gradient update does NOT read the text feedback. The actual model weights are updated solely based on the Scalar Reward (+1 or -1). The GRPO algorithm calculates the advantage: actions (tokens) that led to +1 are amplified, and actions that led to -1 are suppressed.

Takeaway: Textual feedback powers the multi-turn repair (trajectory), but the precise scalar attribution (+1 for valid, -1 for logic failure, masking for exhaustion, INVALID for env failures) is what physically drives the AI's intelligence during backpropagation.
